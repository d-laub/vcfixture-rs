# Per-contig record split (issue #15)

**Status:** approved, ready for implementation
**Issue:** [#15](https://github.com/d-laub/vcfixture-rs/issues/15)
**Baseline:** v0.3.0 (`02b3886`)

## Problem

`Size::Records(total)` and `Size::Target(bytes)` split records across contigs
proportional to each contig's fitted `density_per_kb`. For the built-in
`germline-1kgp` profile that yields a near-uniform corpus (max/min record count
across the 22 autosomes = **1.38×**) even though the same profile's fitted
`n_variants` are strongly skewed (**6.07×**: chr2 at 6,088,598 vs chr21 at
1,002,753).

A flat corpus is harmless for throughput benchmarks and actively misleading for
scheduling ones: contig-level concurrency, load balancing, longest-first
dispatch, and makespan tails are all invisible when every contig finishes at the
same time.

There is also no way — through the library API or the CLI — to express
per-contig record counts directly.

### What v0.3.0 already fixed

The weighting half of this issue **has already landed**, independently, as
`4f241b9` *"fix(bulk): split records by n_variants, not density_per_kb (#10)"*,
released in v0.3.0. `distribute_by_density` is now `distribute_by_n_variants`
and weights by `resolve_contig_stat(...).n_variants`; both `Size::Records` and
both call sites inside `BulkSpec::resolve_target_counts` use it. Issue #15's
option 3 is therefore **done** and needs no code change.

That is the right fix, for the reason the issue gives and one more:
`density_per_kb` is variants *per kb*, so the quantity a record count should be
proportional to is density **times** contig length — which is exactly
`ContigStat::n_variants`, already stored alongside it. Weighting by density
alone implicitly assumed every contig had the same length. Nor did it buy
realistic output density in exchange: generated positions come from
`fitted.gap_dist`, and each contig's declared `##contig` `length` is its
*populated span*, not a real chromosome length (see `BulkSpec`'s "Contig length
rule"), so realized per-kb density is set by `gap_dist` no matter which weight
split the counts.

Because the wrong weight had no compensating benefit, issue #15's option 2 (a
`weight_by: Weight::Density | Weight::Variants` knob) is deliberately **not**
implemented: the only setting it could offer besides today's is the broken one.

### What v0.3.0 left behind

`4f241b9` changed the code and the rustdoc but not everything that described the
old behaviour, and it added no test that can tell the two weights apart:

1. **Stale prose.** `docs/book/src/bulk-generation.md:111` still says "split
   across contigs proportional to each contig's fitted density", and the
   `--records` CLI help in `src/bin/vcfixture.rs:49-50` still says "proportional
   to the profile's fitted density". These are exactly the two sentences issue
   #15's "Doc note" asks to correct.
2. **A non-discriminating test suite.** The `NONUNIFORM_DENSITY_PROFILE` fixture
   in `tests/bulk.rs:419-421` declares `n_variants` 8000/4000/1000 against
   `density_per_kb` 80/40/10 — the *same* 8:4:1 ratio. Every split test passes
   identically under either weight, so nothing in the suite would catch a
   relapse, and `records_total_splits_by_density_and_sums_exactly` still carries
   the old weight in its name and comments.

## Design

Two code changes plus the documentation and test debt above.

### 1. `Size::PerContig(BTreeMap<String, u64>)`

A new `Size` variant carrying explicit per-contig record counts. This is the one
thing neither the weighting fix nor a derived profile can express: it lets a
caller reproduce any real cohort's per-contig shape against a built-in profile
without fitting a new one.

```rust
pub enum Size {
    Records(u64),
    RecordsPerContig(u64),
    PerContig(BTreeMap<String, u64>),
    Target(u64),
}
```

**`BTreeMap`, not `HashMap`.** Stable iteration and stable `Debug` output, in a
crate that is otherwise strict about determinism. Map iteration order does not
affect generated bytes (counts are looked up per entry of `contig_ids`, which is
authoritative for output order), but a deterministic `Debug` is free here.
`Summary::per_contig` is already a `BTreeMap<String, ContigSummary>`, so this
also matches the shape callers already read results back out of.

**`Size` loses `Copy`.** `BTreeMap` is not `Copy`, so the derive becomes
`#[derive(Debug, Clone, PartialEq, Eq)]`. `BulkSpec::write` takes `self` by
value and its `match self.size` would partially move `size` out of `self`,
which then forbids the `&self` method calls later in the function — so it
becomes `match &self.size`, with the two integer variants binding by `&n`.
`BulkSpec::size(self, size: Size)` already takes its argument by value, so the
builder API is source-compatible; only callers relying on an implicit copy of a
`Size` value need to add `.clone()`. Acceptable at 0.x.

**Validation, in `BulkSpec::write`, before any generation** — alongside the
existing empty-contigs, zero-samples, and duplicate-contig-name guards. Both
directions are checked, each producing `BulkError::Invalid` naming the offending
contigs:

- Every entry of `contig_ids` must have a key in the map. A missing entry would
  otherwise silently produce an empty contig.
- Every key in the map must appear in `contig_ids`. An extra key is almost
  always a typo, and ignoring it silently gives the caller a corpus that is not
  what they asked for.

Names are matched **exactly** — no `chr`-prefix normalization. The
normalization rule in `resolve_contig_stat` exists to reconcile caller-chosen
output names with the bare ids (`"1"`, `"2"`) that committed profiles were fit
from; that is a different problem. Here both `contigs` and the `PerContig` keys
come from the same caller in the same call, so an exact match with a loud error
is the honest contract, and normalizing would only add a second, fuzzier way to
spell a contig name.

A count of `0` is legal and means "generate nothing for this contig" — it is
explicitly requested, unlike the missing-key case. `contig_span` already returns
`1` for an empty record set, so a zero-count contig gets a well-formed
`##contig length=1` header entry and no records, with no special-casing.

`PerContig` and `Target` do not interact: `Target` grows a corpus until a byte
size is reached, `PerContig` fixes the counts outright. They are separate
variants and a caller picks one.

### 2. CLI: `--records-for`

```
--records-for chr1=5759060,chr2=6088598 --records-for chr3=5000000
```

Repeatable and comma-delimited (clap `value_delimiter = ','`), each value
`NAME=COUNT`. It conflicts with `--target-size`, `--records`, and
`--records-per-contig`, and those three gain it in their own
`conflicts_with_all` lists, matching how they already conflict pairwise.

**Parsing lives in the library, not the binary.** A new
`pub fn parse_records_for(tokens: &[String]) -> Result<Vec<(String, u64)>, BulkError>`
goes in `src/bulk/mod.rs` next to `parse_size`, which is public for exactly this
reason: `tests/cli.rs` cannot import from a `[[bin]]` target, and it already
tests `parse_size` this way. It returns a `Vec` rather than the `BTreeMap`
because command-line **order** is load-bearing (see below); the caller builds
the map.

It rejects, with the offending token quoted in the message: a token with no
`=`, an empty name, an empty or unparseable count, and a duplicate name.

**`--contigs` becomes `Option<Vec<String>>`.** Today it carries a
`default_values_t` of `chr1,chr2,chr3`, which makes "not supplied"
indistinguishable from "supplied the default". Making it optional lets the CLI
resolve the contig list as:

1. `--contigs` if given;
2. otherwise the `--records-for` names, **in the order written on the command
   line**;
3. otherwise `chr1,chr2,chr3` — today's default, now applied explicitly in
   `run()` rather than by clap.

Without rule 2, a 22-autosome run has to spell out all 22 names twice, in two
places that can drift apart. Rule 3 keeps every existing invocation behaving
exactly as it does now; the only user-visible change is that `--help` no longer
prints a `[default: chr1,chr2,chr3]` annotation, so the help text states the
default in prose instead.

If both `--contigs` and `--records-for` are given they must agree. That is not
checked separately in the CLI: the library's `PerContig` validation already
reports both mismatch directions with the offending names.

### 3. Documentation

- `docs/book/src/bulk-generation.md:105-118` — the "Sizing" section's lead-in
  says "Three ways"; it becomes four. The `Size::Records` bullet's "proportional
  to each contig's fitted density" becomes "proportional to each contig's fitted
  variant count (`n_variants`)", and a `Size::PerContig` / `--records-for`
  bullet is added.
- The same section gains a short note that the built-in human profiles' fitted
  `n_variants` span roughly 6× across the autosomes while their densities span
  only ~1.2×, so `--records` produces a genuinely skewed corpus — and that this
  skew is what makes contig-level scheduling behaviour observable in a
  benchmark, which is the reason to care.
- `src/bin/vcfixture.rs` — the `--records` help text's "proportional to the
  profile's fitted density" becomes "proportional to the profile's fitted
  per-contig variant counts (`n_variants`)".
- `Size::PerContig` gets a rustdoc comment covering the exact-name-match rule
  and that a `0` count is legal.

`CHANGELOG.md` is generated by commitizen from commit messages (`.cz.toml`), so
it is not hand-edited; the feature is carried by a `feat(bulk):` commit subject
and the doc corrections by `docs(bulk):`.

## Testing

**New fixture: `SKEWED_VARIANTS_PROFILE`** in `tests/bulk.rs`. Bare contig ids
`"1"`/`"2"`/`"3"`, **equal** `density_per_kb` across all three, and `n_variants`
in a 6:2:1 ratio. Under the old weight this splits evenly; under the shipped one
it splits 6:2:1. This is the fixture that would have caught issue #15, and it is
the regression guard `4f241b9` did not come with.

Tests to add:

1. `records_total_splits_by_variants_not_density` — with
   `SKEWED_VARIANTS_PROFILE` and `Size::Records(N)`, the split sums to exactly
   `N`, and contig 1 gets several times contig 3's count even though their
   densities are identical. Asserts a direction and a rough magnitude, not exact
   counts, so largest-remainder tie-breaking is not load-bearing.
2. `target_size_split_also_follows_variants` — the same skew is visible in a
   `Size::Target` run's per-contig counts, confirming both call sites use the
   variant weight.
3. `per_contig_gives_exact_requested_counts` — `Size::PerContig` reproduces each
   requested count exactly in the returned `Summary`, including a contig
   requested with count `0`. A zero-count contig never reaches
   `Summary::observe`, so it has no `per_contig` entry at all; the assertion
   reads through `.get(id).map_or(0, |c| c.n_records)` rather than indexing.
4. `per_contig_missing_contig_is_an_error` — a requested contig absent from the
   map errors, and the message names it.
5. `per_contig_unknown_key_is_an_error` — a map key that is not a requested
   contig errors, and the message names it. Uses the near-miss case (`"1"`
   supplied where `"chr1"` was requested) to pin down that names are matched
   exactly, with no `chr`-prefix normalization.
6. `per_contig_ignores_profile_shape` — against `SKEWED_VARIANTS_PROFILE`, an
   *anti-*skewed `PerContig` map (contig 3 given the most records) is honoured
   exactly, proving the profile is not consulted for the split at all.

Tests to update:

- `records_total_splits_by_density_and_sums_exactly` (`tests/bulk.rs:281`) is
  renamed to `records_total_sums_to_exactly_the_requested_total`, and its
  doc comment and inner "chr1's density (80) is 8x chr3's (10)" comment are
  corrected to name `n_variants`. Its assertions still hold against
  `NONUNIFORM_DENSITY_PROFILE` (8:4:1 under either weight), so it stays as
  coverage of the sums-to-exactly-`total` property while test 1 above covers
  the weighting.
- The three `resolve_contig_stat` tests (`bare_id_profile_resolves_by_chr_
  prefix_normalization`, `chr_prefix_normalization_resolves_by_name_not_
  position`, `unrelated_contig_names_fall_back_positionally_without_erroring`)
  keep passing unchanged, but their comments say "density 80" / "density 10" and
  are corrected to name the fitted variant counts.

CLI coverage in `tests/cli.rs`: `parse_records_for` over the single-token,
comma-delimited, and multi-flag forms, plus each rejection case (no `=`, empty
name, unparseable count, duplicate name).

## Out of scope

- A `weight_by` knob on `Size::Records` (issue #15 option 2). See "What v0.3.0
  already fixed".
- Re-fitting or altering any committed profile JSON.
- Reading per-contig counts from a TSV file. The repeatable, comma-delimited
  `--records-for` already fits 22 autosomes on one command line; a file loader
  is a second way to do the same thing and can be added if a caller wants it.
- Removing `density_per_kb` from `ContigStat`. It is unread after `4f241b9`, but
  it is fitted provenance and part of the serialized profile schema; dropping it
  would invalidate every committed profile JSON for no benefit.

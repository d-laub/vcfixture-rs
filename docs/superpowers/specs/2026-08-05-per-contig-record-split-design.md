# Per-contig record split (issue #15)

**Status:** approved, ready for implementation
**Issue:** [#15](https://github.com/d-laub/vcfixture-rs/issues/15)

## Problem

`Size::Records(total)` and `Size::Target(bytes)` split records across contigs
proportional to each contig's fitted `density_per_kb`. For the built-in
`germline-1kgp` profile that yields a near-uniform corpus (max/min record count
across the 22 autosomes = **1.38×**) even though the same profile's fitted
`n_variants` are strongly skewed (**6.07×**: chr2 at 6,088,598 vs chr21 at
1,002,753).

A flat corpus is harmless for throughput benchmarks and actively misleading for
scheduling ones: contig-level concurrency, load balancing, longest-first
dispatch, and makespan tails are all invisible when every contig finishes at the
same time.

There is currently no way — through the library API or the CLI — to express
per-contig record counts directly.

### Why the current weight is wrong, not merely unhelpful

`density_per_kb` is variants *per kb*. The quantity a record count should be
proportional to is variants-per-kb **times** contig length — which is exactly
`ContigStat::n_variants`, already stored alongside it. Weighting by density
alone implicitly assumes every contig has the same length. The human autosomes
have fairly uniform density (~21–26 variants/kb) and very non-uniform length, so
weighting by density discards nearly all the real between-contig variation.

Nor does density weighting buy realistic output density in exchange. Generated
positions come from `fitted.gap_dist`, and each contig's declared `##contig`
`length` is its *populated span*, not a real chromosome length (see
`BulkSpec`'s "Contig length rule"). Realized per-kb density in the output is
therefore set by `gap_dist` regardless of which weight was used to split the
record counts. `density_per_kb` is read in exactly one place —
`distribute_by_density` in `src/bulk/mod.rs` — and nothing about the output
depends on its being the weight.

Because the wrong weight has no compensating benefit, this is treated as a **bug
fix**, not as a new behaviour toggle. Issue #15's option 2 (a
`weight_by: Weight::Density | Weight::Variants` knob) is deliberately **not**
implemented: once the weight is correct, the only other setting the knob could
offer is the broken one.

## Design

Three code changes — one internal, two to the public surface — plus the
documentation they invalidate.

### 1. Weight the split by fitted `n_variants`

`distribute_by_density` is renamed `distribute_by_variants` and weights each
contig by `resolve_contig_stat(fitted, i, id).n_variants` instead of
`.density_per_kb`.

Everything else about the helper is unchanged:

- Largest-remainder apportionment, so the per-contig counts sum to exactly
  `total`.
- Even-split fallback when every resolved weight is zero (degenerate profile),
  rather than dividing by zero.
- Contig-name resolution still goes through `resolve_contig_stat`, so
  `chr`-prefix normalization and the positional last resort are untouched.

Both callers pick the fix up automatically: `Size::Records` in `BulkSpec::write`
and both the initial guess and each round's top-up in
`BulkSpec::resolve_target_counts`.

`n_variants` is a `u64`; the weights vector stays `f64` (`n_variants as f64`) so
the existing proportional arithmetic is unchanged. Fitted counts are at most
~6.1e6 per contig for the built-in profiles, far inside f64's exact-integer
range, so the cast is lossless in practice and the zero-weight guard still fires
correctly for an all-zero profile.

This is a behaviour change for existing callers of `Size::Records` and
`Size::Target`. The crate is pre-1.0; the change is called out in the commit
message and in the book.

### 2. `Size::PerContig(BTreeMap<String, u64>)`

A new `Size` variant carrying an explicit per-contig record count. This is the
one thing a derived profile cannot express: it lets a caller reproduce any real
cohort's per-contig shape against a built-in profile without fitting a new one.

```rust
pub enum Size {
    Records(u64),
    RecordsPerContig(u64),
    PerContig(BTreeMap<String, u64>),
    Target(u64),
}
```

**`BTreeMap`, not `HashMap`.** Stable iteration and stable `Debug` output, in a
crate that is otherwise strict about determinism. Map iteration order does not
affect generated bytes (counts are looked up per entry of `contig_ids`, which is
authoritative for output order), but a deterministic `Debug` is worth having for
free.

**`Size` loses `Copy`.** `BTreeMap` is not `Copy`. The derive becomes
`#[derive(Debug, Clone, PartialEq, Eq)]`, and the one internal
`match self.size` in `BulkSpec::write` becomes `match &self.size`.
`BulkSpec::size(self, size: Size)` already takes its argument by value, so the
builder API is source-compatible; only callers that relied on implicit copies of
a `Size` value need a `.clone()`. Acceptable at 0.1.

**Validation, in `BulkSpec::write`, before any generation.** Both directions are
checked and both produce `BulkError::Invalid` listing the offending names:

- Every entry of `contig_ids` must have a key in the map. A missing entry would
  otherwise mean a silently empty contig.
- Every key in the map must appear in `contig_ids`. An extra key is almost
  always a typo, and silently ignoring it is how a caller ends up with a corpus
  that does not match what they asked for.

Names are matched **exactly** — no `chr`-prefix normalization. The normalization
rule in `resolve_contig_stat` exists to reconcile caller-chosen output names
with the bare ids (`"1"`, `"2"`) that committed profiles were fit from; that is
a different problem. Here both `contigs` and the `PerContig` keys come from the
same caller in the same call, so an exact match with a loud error is the honest
contract, and normalizing would only create a second, fuzzier way to spell a
contig name.

A zero count for a contig is legal and means "generate nothing for this contig"
— it is explicitly requested, unlike the missing-key case.

`PerContig` and `Target` do not interact: `Target` grows a corpus until a byte
size is reached, `PerContig` fixes the counts outright. They are separate
variants and a caller picks one.

### 3. CLI: `--records-for`

```
--records-for chr1=5759060,chr2=6088598 --records-for chr3=5000000
```

Repeatable and comma-delimited (clap `value_delimiter = ','`), each value
`NAME=COUNT`. Parse errors (no `=`, empty name, unparseable count, duplicate
name) are reported with the offending token.

`--records-for` conflicts with `--target-size`, `--records`, and
`--records-per-contig`, matching how those three already conflict pairwise.

**`--contigs` becomes `Option<Vec<String>>`.** Today it carries a
`default_values_t` of `chr1,chr2,chr3`, which makes "not supplied"
indistinguishable from "supplied the default". Making it optional lets the CLI
resolve the contig list as:

1. `--contigs` if given;
2. otherwise the `--records-for` keys, **in the order they were written on the
   command line**;
3. otherwise `chr1,chr2,chr3` (today's default, applied explicitly).

Without rule 2, a 22-autosome run has to spell out all 22 names twice, in two
places that can drift apart. To preserve command-line order, the CLI parses into
a `Vec<(String, u64)>` and only then builds the `BTreeMap`; the map is order-
insensitive but `contig_ids` is not.

If both `--contigs` and `--records-for` are given they must agree — that is not
checked separately in the CLI, because the library's `PerContig` validation
already reports both mismatch directions with the offending names.

### 4. Documentation

Four places currently describe the split as "proportional to the profile's
fitted density" and become "proportional to the profile's fitted per-contig
variant counts (`n_variants`)":

- `Size::Records`'s doc comment (`src/bulk/mod.rs`).
- `Size::Target`'s doc comment, which cross-references it.
- The `--records` help text (`src/bin/vcfixture.rs`).
- `docs/book/src/bulk-generation.md`'s `Size` bullet list, which also gains a
  bullet for `Size::PerContig` / `--records-for`.

The book gains a short note that the built-in human profiles' per-contig
`n_variants` span roughly 6× across the autosomes, so `--records` produces a
skewed corpus — and that this is what makes contig-level scheduling behaviour
observable in a benchmark.

`CHANGELOG.md` is generated by commitizen from commit messages (`.cz.toml`), so
it is not hand-edited; the behaviour change is carried by a `fix(bulk):` commit
subject and the feature by a `feat(bulk):` one.

## Testing

The existing `NONUNIFORM_DENSITY_PROFILE` fixture in `tests/bulk.rs` declares
`n_variants` 8000/4000/1000 against `density_per_kb` 80/40/10 — the *same* 8:4:1
ratio. Every current split test therefore passes under either weight and none of
them discriminate between the old and new behaviour. That gap is the first thing
to close.

**New fixture: `SKEWED_VARIANTS_PROFILE`.** Bare contig ids `"1"`/`"2"`/`"3"`,
**equal** `density_per_kb` across all three, and `n_variants` in a 6:2:1 ratio.
Under the old weight this splits evenly; under the new one it splits 6:2:1. This
is the fixture that would have caught issue #15.

Tests to add:

1. `records_total_splits_by_fitted_variants` — with `SKEWED_VARIANTS_PROFILE`
   and `Size::Records(N)`, the split sums to exactly `N` and tracks the 6:2:1
   variant ratio, not the uniform density. Asserts a direction and a rough
   magnitude, not exact counts, so largest-remainder tie-breaking is not
   load-bearing.
2. `target_size_split_also_follows_variants` — the same skew is visible in a
   `Size::Target` run's per-contig counts, confirming both call sites moved.
3. `per_contig_gives_exact_requested_counts` — `Size::PerContig` reproduces
   each requested count exactly in the emitted `.summary.json`, including a
   contig requested with count 0.
4. `per_contig_missing_contig_is_an_error` — a requested contig absent from the
   map errors, and the message names it.
5. `per_contig_unknown_key_is_an_error` — a map key that is not a requested
   contig errors, and the message names it. Includes the near-miss case
   (`"1"` supplied where `"chr1"` was requested) to pin down that names are
   matched exactly, with no `chr`-prefix normalization.
6. `per_contig_beats_profile_shape` — `PerContig` counts win over whatever the
   profile's fitted proportions would have produced, i.e. the profile is not
   consulted for the split at all.

Existing tests to update:

- `records_total_splits_by_density_and_sums_exactly` is renamed and its comment
  corrected to name `n_variants` as the weight. Its assertion still holds
  against `NONUNIFORM_DENSITY_PROFILE` (8:4:1 either way), so it stays as
  coverage of the sums-to-exactly-`total` property.
- The three `resolve_contig_stat` tests (`bare_id_profile_resolves_by_chr_
  prefix_normalization`, `chr_prefix_normalization_resolves_by_name_not_
  position`, `unrelated_contig_names_fall_back_positionally_without_erroring`)
  keep passing unchanged, since that fixture's two weights agree — but their
  comments say "density 80" and are updated to name the fitted variant counts.

CLI coverage: a test for `--records-for` parsing including the repeat + comma
forms, the contigs-derived-from-keys rule, and a malformed-token error.

## Out of scope

- A `weight_by` knob on `Size::Records` (issue #15 option 2). See "Why the
  current weight is wrong" above.
- Reading per-contig counts from a TSV file. `--records-for`'s repeatable,
  comma-delimited form already fits 22 autosomes on one command line; a file
  loader is a second way to do the same thing and can be added if a caller
  actually wants it.
- Removing `density_per_kb` from `ContigStat`. It becomes unread after this
  change, but it is fitted provenance and part of the serialized profile schema;
  dropping it would invalidate every committed profile JSON for no benefit.
